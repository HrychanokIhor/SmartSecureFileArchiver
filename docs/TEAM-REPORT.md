## Задачі для автора LZ77

Гілка feature/Stream-Parsing містить LiteralToken(Value), MatchToken(Distance,Length) і ILz77Token. Ці типи існують у гілці, хоча їх немає в поточній main та попередньо перевіреній комбінації PR №4–8. Не потрібно писати їх повторно.

Потрібен адаптер на межі модулів:

```csharp
// Після спільного підключення типів обох модулів:
HuffmanToken ToHuffman(ILz77Token token) => token switch
{
    LiteralToken literal => HuffmanToken.FromLiteral(literal.Value),
    MatchToken match when match.Length > 0 && match.Length <= ushort.MaxValue
        && match.Distance > 0 && match.Distance <= ushort.MaxValue
        => HuffmanToken.FromMatch((ushort)match.Length, (ushort)match.Distance),
    _ => throw new InvalidDataException("Непідтримуваний LZ77-токен.")
};
```

HuffmanToken належить SmartArchiver.Core.Services.Huffman; LZ77 ILz77Token — SmartArchiver.Core.Interfaces, моделі — SmartArchiver.Core.Models. Зворотне перетворення: literal → new LiteralToken(value), match → new MatchToken(distance,length). Зверни увагу: FromMatch приймає length перед distance, а конструктор MatchToken — distance перед length.

Поточний Huffman підтримує додатні length/distance до 65535. Якщо LZ77 дозволяє більші значення, потрібно погодити обмеження або змінити подання до інтеграції. Перевірка distance проти відновленої історії — відповідальність LZ77-декодера. Старий Lz77Token(Offset,Length,NextByte) не тотожний цій моделі; не додавати зайвий байт після останнього посилання.

Локальний merge-tree підтвердив відсутність текстового конфлікту між f0ad40d і origin/feature/Stream-Parsing 8cc6b9d. Це не перевірка працездатності їх спільного pipeline: адаптер і наскрізний тест ще потрібні.

## Задачі для інтегратора

1. Узгодити остаточний token API з автором LZ77. Не змінювати одночасно namespaces в різних гілках без оновлення використань.
2. Схема стиснення: LZ77 → адаптер → Lz77HuffmanCodec.Compress → три пари Header/Data → payload → пакування/шифрування. Зворотний шлях: перевірка HMAC/розшифрування → розбір payload → Huffman.Decompress → адаптер → LZ77 decode → CRC32.
3. Block не є готовими байтами архіву. Для першої демонстрації потрібно явно описати контейнер трьох пар Header/Data з їх довжинами; остаточний wire format узгодити з FORMAT_SPEC.
4. NO_COMPRESSION обходить LZ77 і Huffman: зберігати raw bytes; coded_len == raw_len, overhead рахувати окремо. Створення LiteralToken для кожного байта не гарантує цей режим.
5. Викликати codec на обмежених блоках; не читати весь великий файл у RAM. maxTokens/maxSymbols задавати відповідно до конфігурації; стандартний ліміт — 16 Mi символів, це не розмір файла в байтах і не streaming API.
6. Для томів враховувати 73 байти header+HMAC плюс службовий payload; W рюкзака визначати після резервування таблиці всіх файлів-кандидатів. Вага блока за методичкою coded_len+15.
7. Перевіряти безпечні імена, структуру payload, відсутні/дубльовані томи та атомарний запис. HMAC не замінює ці перевірки.
