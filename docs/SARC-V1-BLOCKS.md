# Стиснуті блоки SARC v1

`SarcBlockCodec` реалізує §3 `FORMAT_SPEC_P2`. `SarcPipeline` тепер використовує цей кодек для одного стиснутого блока. Попередні API `HUF1` залишаються для окремих експериментів; їхній формат не використовується в новому блоці.

- Три канонічні таблиці LIT/LEN/DIST передують одному бітовому потоку. Поля записуються big-endian, біти — MSB-first.
- LIT 256 означає посилання. LEN зберігає довжину мінус 3, DIST — бітову довжину відстані мінус 1 (тобто bit_length(distance − 1)); за DIST йдуть молодші біти.
- Package-merge підбирає довжини не більше 15 біт, зберігаючи всі символи. Декодер перевіряє алфавіти, довжини, точну рівність Крафта, посилання на вже відновлені дані та нульове доповнення.
- Некоректні коди повертають `ArchiveException(E_CODE)`, неузгоджені розміри або зайві байти — `ArchiveException(E_PAYLOAD)`.

## Підключення

Інтегратор передає в `SarcPipeline.Decompress(codedBlock, rawLength)` рівно `coded_len` байтів та перевірений `raw_len`. Для `NO_COMPRESSION` викликати кодек не потрібно: зберігаються початкові байти. API `SarcBlockCodec.Encode/Decode` підходить для готових токенів як жадібного, так і лінивого розбору; `SarcPipeline.Compress` використовує лінивий.

Це формат блока, а не реалізація таблиць файлів, пакування томів чи повного CLI. Старі експериментальні блоки з трьома потоками не сумісні з цим форматом.

## Перевірка

`SarcPipelineTests` містить 57-байтовий вектор §8, незалежний вектор для одного символу, межі LZ77, блок 16 КіБ, перекошені частоти та некоректні входи. Очікуваний результат §8: 480 байтів `hello world ` × 40, CRC32 `70208846`.
